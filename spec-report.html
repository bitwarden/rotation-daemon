1Overview

The Bitwarden Rotation Daemon is a service that automatically rotates credentials (passwords) for external systems — Microsoft Entra users, MSSQL accounts, or anything reachable by a custom script — on behalf of a Bitwarden organization. When it rotates a credential, it updates the account on the target system and writes the new password back into the Bitwarden vault cipher so it's always current.

The system is split across two spec files that form a clean boundary:

FileResponsibility
rotation-daemon.alliumThe daemon process: connects to the Bitwarden server, claims rotation jobs, executes them against target systems, writes the new password back to the vault.
rotation-server.alliumThe Bitwarden server side: registers target systems and daemon identities, manages rotation configurations and schedules, creates rotation jobs, orchestrates retries, handles recovery, and emits the audit trail.
🔐
Zero-knowledge by design. The server never holds a plaintext organization key or plaintext password. The daemon decrypts the org key locally using a local encryption_key that is never transmitted. Every password written to the vault is ciphertext encrypted client-side. The server stores and forwards it without ever seeing the plaintext.

4State Machines

Six entities carry explicit status state machines. Understanding these is key to following any flow.

ServerConnection

The persistent connection between the daemon and the Bitwarden server. It is never terminal — a disconnection always triggers a reconnect attempt with exponential backoff.

ServerConnection status
stateDiagram-v2 direction LR [*] --> connecting connecting --> connected : auth succeeds\n(OpenConnection) connecting --> disconnected : auth rejected\n(RefuseConnection) connected --> disconnected : server interrupts\n(ServerInterruptsConnection) disconnected --> connecting : auto-reconnect\n(Reconnect, backoff)
ℹ
The connection becomes connected only once authentication succeeds — not at the TCP/WebSocket layer. This ensures the daemon never attempts task execution without a valid session.

DaemonSession

The daemon's authenticated session. One session is created per connection attempt. revoked is terminal: the daemon cannot reconnect until issued a new credential.

DaemonSession status
stateDiagram-v2 direction LR [*] --> authenticating : DaemonConnects authenticating --> active : HandleAuthenticationSucceeded authenticating --> revoked : HandleAuthenticationRejected active --> expired : SessionExpires\n(access token TTL lapses) active --> revoked : HandleSessionRevoked\n(admin revokes daemon) expired --> authenticating : RefreshSession\n(re-presents credential) revoked --> [*]

When active, the session holds three values: access_token, expires_at, and organization_key. The org key is derived by decrypting the server's response with the local encryption_key — the server never sees the plaintext.

RotationAttempt

One execution attempt of a rotation. The server creates a fresh attempt each time a daemon claims a job. The daemon executes it exactly once — it does not retry internally. If it fails, the server decides whether to make the job claimable again for a fresh attempt.

RotationAttempt status
stateDiagram-v2 direction LR [*] --> pending : ReceiveGrant\n(daemon claims job) pending --> executing : ReceiveAttempt executing --> succeeded : HandleRotationSucceeded executing --> failed : MarkAttemptFailed succeeded --> [*] failed --> [*]

RotationJob

The server's tracking record for one rotation occurrence. A job starts pending — available for any eligible daemon to claim. The claimed → pending edge is the retry mechanism: a failed attempt with budget remaining returns the job to claimable after a backoff, ready for a fresh claim.

RotationJob status
stateDiagram-v2 direction LR [*] --> pending : OfferRotation pending --> claimed : ClaimRotation\n(daemon takes job) pending --> timed_out : JobTimesOut\n(deadline exceeded) claimed --> pending : RetryJob\n(attempt failed, retries left) claimed --> succeeded : MarkJobSucceeded\n(attempt → succeeded) claimed --> failed : FailJob\n(attempt_count ≥ max_attempts) claimed --> lost : DaemonConnectionDropsLoseJobs claimed --> timed_out : JobTimesOut\n(deadline exceeded) succeeded --> [*] failed --> [*] lost --> [*] timed_out --> [*]
⚠
When a job goes lost, its rotation config's next_rotation_at is set to now, making it immediately due for a fresh OfferRotation. No rotation is permanently lost across a connection drop.

DaemonConnection

The server's per-daemon record of connection liveness. One DaemonConnection is created per registered daemon (starting disconnected). The server flips it when the daemon's authenticated transport comes up or down. Routing and per-daemon recovery both read this — a daemon only receives dispatches while connected, and only its own in-flight dispatches are lost when it drops.

SessionTermination

Post-rotation cleanup: terminates active sessions for the rotated account. Completely independent of the rotation task — abandoned does not fail the rotation.

5Connection & Authentication

When the daemon starts, it immediately begins connecting. The connection only becomes usable once the daemon has authenticated and received an organization key it can use to encrypt vault writes.

Token expiry and refresh

Access tokens are short-lived. When session.expires_at ≤ now, the rule SessionExpires fires and transitions the session to expired, which immediately triggers RefreshSession to move it back to authenticating. The daemon re-presents its credential and gets a fresh token without admin intervention.

Revocation

An admin can revoke a daemon from the server UI. This triggers HandleSessionRevoked → session goes revoked (terminal). The server also closes the connection. The daemon cannot reconnect until issued a new DaemonCredential. (How re-issuance works is an open question — see §14.)

♾
Invariant: AtMostOneActiveSession — at any point at most one DaemonSession may be active. A refresh creates a new session in authenticating before the old one expires.

6Rotation Triggers

A rotation can be triggered in three ways. All three converge on a single choke point — OfferRotation — that enforces all eligibility guards before creating a pending job that daemons can claim.

How triggers converge on OfferRotation
flowchart TB T1["⏱ Scheduled\nRotationDue\n(next_rotation_at ≤ now)"] T2["👤 On-demand\nTriggerRotationNow\n(admin clicks 'Rotate now')"] T3["🔑 Access event\nRotateOnAccessEnd\n(PAM/AAP grant ended)"] DP["OfferRotation(rotation_config, source)"] T1 --> DP T2 --> DP T3 --> DP PD{"OfferRotation\nguards"} DP --> PD G1["✓ config.enabled"] G2["✓ mode = automatic"] G3["✓ no active job"] G4["✓ registration active"] PD --> G1 PD --> G2 PD --> G3 PD --> G4 G1 & G2 & G3 & G4 --> OUT["Create RotationJob (pending)\nServer notifies eligible daemons\nDaemon claims → RotationAttempt"] style PD fill:#fff0e6,stroke:#a04000 style OUT fill:#e8f5ed,stroke:#1a7d3b

The three triggers explained

Scheduled (RotationDue). Fires as a temporal trigger when rotation_config.next_rotation_at ≤ now. Only fires when a schedule exists — a config with no schedule never has a next_rotation_at, so this trigger never fires for it.

On-demand (TriggerRotationNow). An admin triggers rotation immediately from the RotationConfigView surface. Useful for immediate need or testing. Only available for automatic-mode configs.

On access end (RotateOnAccessEnd). An upstream access-control system (PAM leasing, AAP, etc.) signals via AccessEventIntake that a grant over a managed credential has ended. The cipher alone identifies the config (one config per cipher). The config must have rotate_on_access_end = true.

Manual configurations

Configs with mode = manual skip all triggers. When they become due, awaiting_manual_rotation is surfaced to administrators. The rotation is performed out-of-band and recorded via RecordManualRotation. See §11.

7Rotation Execution

Once a daemon claims a job and receives a RotationGranted response, it creates a RotationAttempt and executes a fixed sequence of steps. Each attempt is independent and always starts from step 1 — a fresh password is generated so the target system and vault cipher stay in sync even after a partial failure.

Server-orchestrated retries

If any step fails, RotationAttemptFailed is raised. The daemon calls MarkAttemptFailed — it does not retry internally. The server observes the attempt transition to failed and decides what happens next:

  • If job.attempt_count < max_attempts (5), RetryJob returns the job to pending with a backoff delay (next_claimable_at = now + retry_base_delay). Any eligible daemon can then claim the job — the same one or another assigned daemon, giving natural failover.
  • When attempts are exhausted, FailJob marks the job failed, reschedules the config to now + failure_retry_delay (1 hour), and emits RotationFailed as the seam for a future failure-handling policy (§6.8 — an open question).
⚠
Important: A failed rotation is not silently advanced to the next scheduled occurrence. The config is rescheduled to a near-term retry window (1 hour) so it tries again soon. The schedule only advances on success. Each retry is a fresh claim — it may land on a different daemon than the previous attempt.

8Cipher Write Authorization

The daemon holds the organization key, which in principle could encrypt writes to any cipher in the org vault. The spec scopes that write authority to the specific cipher being rotated by using the in-flight RotationJob itself as the capability — no separate token or grant entity is needed.

🔑
How it works: when the daemon submits a cipher write (SubmitCipherUpdate), the server looks up the RotationJob for that attempt's cipher and checks two things: the job is claimed by this daemon (job.daemon = writer), and the job is still claimed. Both must hold; otherwise the write is rejected and audited. There is no time window — ownership and in-flight status are the full check.

Why the claimed job is sufficient

The job is created by the server and records which daemon claimed it (job.daemon). A write is only accepted from that specific daemon, while the job is still claimed. A timed-out, lost, or completed job is no longer claimed, so a stale write from an abandoned attempt is refused automatically — without needing a time window or a separate nonce.

The write is a full-object PUT (today's API has no partial-content update): the daemon GETs the cipher, swaps in the newly-encrypted password, and re-PUTs the whole object. The claimed job authorises replacing the entire cipher record, not just the password field. A dedicated partial-update endpoint would tighten this further — it's noted as an open question.

API-scoped reads

Defence in depth on the read side: the daemon's credential carries no general cipher-read scope. The server will not enumerate ciphers for it or serve ciphertext for any cipher except the one currently being rotated (a claimed job). This limits what a compromised org key can actually expose without also breaching the server-side API authorization.

♾
Guarantee: JobBoundWrite (on CipherWriteIntake) — a cipher write is accepted only against a RotationJob claimed by this daemon (job.daemon = writer, job.status = claimed). The target is the attempt's cipher; the daemon cannot redirect the write elsewhere. The server stores only ciphertext (zero-knowledge).
♾
Guarantee: ApiScopedReads (on CipherWriteIntake) — the daemon's credential has no general cipher-read scope. Only the cipher actively being rotated (claimed job) is readable, so the organization key cannot be turned into broad vault disclosure without also breaching server-side API authorization.

9Session Termination

After a successful rotation, if attempt.terminate_sessions = true and the target system has supports_session_termination = true, a SessionTermination is created. Its purpose is to kick existing authenticated sessions for the rotated account — forcing anyone holding the old password to re-authenticate.

Session termination — relationship to rotation

Session termination has its own retry counter — up to max_retry_attempts (5) attempts with exponential backoff — completely independent of the rotation attempt's counter. A termination failure that exhausts retries results in abandoned, which is surfaced to the server but does not fail the rotation. The rotation attempt already succeeded when the cipher was written.

10Recovery from Dropped Connections

When a daemon's connection drops, the server cannot confirm which jobs completed. The recovery mechanism ensures nothing is permanently lost: every job claimed by that daemon is marked lost, made immediately re-due, and offered fresh for any eligible daemon to claim.

What "immediately due" means

Setting next_rotation_at = now makes the config eligible for RotationDue. That trigger creates a fresh pending RotationJob via OfferRotation, which any eligible connected daemon can claim. Because the original job is now lost (no longer claimed), a stale write from the pre-drop attempt would be rejected by RejectCipherUpdate — the job is no longer claimed, so the write check fails.

✓
This design achieves at-least-once rotation delivery: a job that was in-flight during a drop will be re-offered after the drop. The AtMostOneActiveJobPerConfig invariant ensures no duplicate concurrent execution. Recovery is scoped per-daemon: only jobs claimed by the dropped daemon are lost; other daemons' work is unaffected.

11Manual Rotation Fallback

Not every target system has an automated integration the daemon can reach. A rotation config with mode = manual tracks the obligation and records out-of-band compliance.

Manual rotation lifecycle

The key rules:

  • A manual config can only target a system where supports_automatic_rotation = false.
  • Manual configs are never offered as jobs (invariant: ManualConfigNeverJobbed).
  • RecordManualRotation advances the schedule exactly as a successful automatic rotation would — the audit trail gets an honest record without pretending the system can self-rotate.

13Invariants

The spec declares eight invariants — structural properties that must hold at all times. Violations indicate a bug.

AtMostOneActiveSession (daemon)

At most one DaemonSession may be active at any point. Prevents split-brain where two sessions both hold an active org key.

OneRegistrationPerTargetSystem (server)

A TargetSystem has at most one TargetSystemRegistration. Keeps a single, unambiguous active/disabled state per target so the offer guard and assignment lookups can't disagree.

OneConfigPerCipher (server)

A Cipher is under at most one RotationConfig. This is what makes the access-event trigger work: a cipher uniquely resolves the config to rotate, so the signal carries only the cipher ID.

AtMostOneActiveJobPerConfig (server)

A RotationConfig has at most one pending-or-claimed job at a time. Makes the attempt-to-job correlation unambiguous and prevents duplicate concurrent executions of the same credential rotation.

AutomaticConfigTargetsCapableSystem (server)

A RotationConfig with mode = automatic can only target a TargetSystem where supports_automatic_rotation = true. Prevents dispatching to systems the daemon can't actually reach.

ManualConfigNeverJobbed (server)

A RotationConfig with mode = manual has zero jobs. Manual rotations are recorded out-of-band via RecordManualRotation; the daemon never touches them. (See §11.)

OneAssignmentPerDaemonTarget (server)

At most one DaemonTargetAssignment per (daemon, target system) pair. Keeps the eligibility relation clean — a daemon is either assigned a target or it isn't.

OneConnectionPerDaemon (server)

Each DaemonRegistration has exactly one DaemonConnection record, created with the registration (starting disconnected). It is the single source of truth for that daemon's liveness, read by both claim eligibility and per-daemon recovery.

14Open Questions

Fifteen design questions remain unresolved. They are grouped below by topic.

Security & authorization

Read blast radius

The job-bound write and API-scoped read controls contain the blast radius at the authorization layer, but the org key itself remains the theoretical crypto ceiling — a key compromise combined with an API authorization bypass would expose the org vault. Closing it at the crypto layer (so a stolen key reveals nothing beyond the managed cipher) requires per-cipher item keys or a write-only asymmetric scheme; both depend on Bitwarden per-item cipher key support. Deferred.

Cipher write granularity

With no partial-content API, rotation re-PUTs the whole cipher, so the in-flight job authorises replacing the entire cipher (not just its password field) and requires a read-before-write. A dedicated partial-update/rotate endpoint would remove the read and tighten write scope. A separate bearer write-token (a field on the job) would add defence in depth against an ownership-check bug. Both deferred.

Credential re-issuance

Once a daemon's credential is revoked the session is terminal. How is a replacement credential provisioned and delivered to the daemon? There's currently no mechanism for this in the spec.

Scheduling & job lifecycle

Non-cron cadences

Schedule carries a cron expression. Do interval-style presets (e.g. "every 90 days") need a separate representation, or can all UX presets be expressed as cron?

Failure handling (§6.8)

FailJob and JobTimesOut reschedule to now + failure_retry_delay (1 hour) and emit RotationFailed as a seam. §6.8 should define the real policy — alerting, auto-disable after a threshold — and take ownership of next_rotation_at on terminal failure.

Unroutable-job escalation

A job that stays pending because no eligible daemon is connected or assigned currently waits until claimed or until JobTimesOut. Past a threshold it should escalate to an operator; delivery shares the unspecified alerting seam with manual-obligation escalation and §6.8 failure handling.

On-demand audit attribution

On-demand and access-triggered jobs record a source but not the triggering admin. Only manual_recorded carries an actor. Should the audit attribute the on-demand actor end-to-end?

Fleet & routing

Rotation throttling

Many credentials on one target coming due together could hammer that target or connector. This is deliberately not modelled server-side — no fleet-scale deployment is assumed — so there is no longer a per-target concurrency cap. If throttling becomes necessary, the spec's position is that it belongs in the daemon/connector rather than the server scheduler.

Daemon connectivity edges

MarkDaemonConnected/MarkDaemonDisconnected react to server-observed events. Reconcile which daemon-side transitions (ServerConnection / DaemonSession in rotation-daemon.allium) raise each edge — in particular whether a session expiry that is not a transport drop counts as disconnected for routing.

Configuration lifecycle

Mode switching

Can an admin move a RotationConfig between automatic and manual after creation? If so, what happens to its schedule and any active job? The ManualConfigNeverJobbed invariant assumes mode is fixed at creation.

Cancel vs. stop-new on state changes

Disabling a target system, pausing a config, applying new settings, or unassigning a daemon currently only stop new jobs from being offered — claimed jobs are unaffected. Should any of these operations cancel in-flight work?

Manual obligation escalation

Beyond surfacing awaiting_manual_rotation, should a manual config whose obligation stays unmet past a threshold escalate — send a notification, raise severity, or trigger an alert?

Integrations & future scope

Access-event emitter binding

Which upstream systems wire into AccessGrantEnded? The signal shape is resolved (just the cipher ID), but the concrete set of emitters and how they register against AccessEventIntake is open. PAM leases and AAP grants are the expected first consumers.

Custom script result format

When a CustomScript target runs, how does the daemon interpret the result? Exit code is simplest and most portable, but stdout parsing or structured output may be needed for richer error reporting.

Secrets Manager support (Phase 1 non-goal)

A future configuration would point at an SM secret rather than a vault cipher. The cipher field on RotationConfig and daemon/RotationAttempt.cipher are the intended seam. The scheduling, offer/claim, recovery, and audit machinery is designed to carry an SM rotation unchanged — but this needs confirmation before generalising.
