Specification Report

Bitwarden Credential Rotation

A connected daemon rotates credentials inside target systems on behalf of the Bitwarden server. The server schedules and dispatches rotation work as pull-based jobs; the daemon claims a job, executes one attempt, and writes the new (encrypted) password back into the vault cipher — all without the server ever holding a plaintext key or password.

rotation-server.allium — server side (owns scheduling, jobs, targets, config) rotation-daemon.allium — daemon side (executes one attempt, reports outcome) Layering: server uses daemon (one-way)

1Overview

Bitwarden manages secrets in an organization vault. This system keeps the credentials behind those secrets fresh by rotating them in the real target systems that own them — an Entra directory, a SQL Server account, or anything reachable by a custom script — and then writing the new password back into the matching vault Cipher.

Pull-based jobs

When a rotation becomes due the server publishes an available RotationJob. It does not push work at a daemon; an eligible daemon claims the job. A retry is just a re-claim.

One attempt per claim

The daemon executes a single RotationAttempt per claim and reports success or failure. It owns no scheduling, no retry orchestration across attempts, and no target definitions.

Zero-knowledge writes

The daemon encrypts the new password with the organization key (delivered encrypted, decrypted locally) and the server stores only ciphertext. It never sees a plaintext password or key.

In one sentence

The server decides what rotates and when, hands the work to a daemon it trusts for that target, and the daemon does the rotation against the live system and writes the result back — authorised by the very job it claimed, with no separate write token and no plaintext crossing the server.

2The two sides and their boundary

The system is modelled as two specs with a strict one-way dependency. The server spec uses the daemon spec (use "./rotation-daemon.allium" as daemon), so the server may reference daemon types by qualified name (daemon/Cipher, daemon/RotationAttempt), but the daemon can never reference server types. That asymmetry is deliberate: the daemon works only from a self-contained snapshot handed to it on each claim.

Server owns

  • Target-system definitions (TargetSystem) — name, method, kind, password policy, status. No connection details.
  • Daemon identities & eligibility (DaemonRegistration, DaemonTargetAssignment, DaemonConnection).
  • Rotation configuration & triggers (RotationConfig, Schedule, RotationSettings).
  • Scheduling, dispatch, job tracking, retry orchestration, timeout, recovery (RotationJob).
  • Cipher-write authorisation and audit emission.

Daemon owns

  • The transport link (ServerConnection) and authenticated session (DaemonSession).
  • Executing one rotation (RotationAttempt) for the kind carried on the claim.
  • Resolving connection details from local config keyed by target_system_id (e.g. <id>.username).
  • Generating a policy-compliant password and writing back the encrypted cipher.
  • Best-effort session termination (SessionTermination) and local transient retry.

6Cross-cutting topics

Authentication & authorisation

OAuth client-credentials

The daemon authenticates with a provisioned DaemonCredential (client_id + client_secret), exchanged for a short-lived bearer access token (DaemonConnects → HandleAuthenticationSucceeded). Borrows Secrets Manager's token pattern.

Claim-time token re-validation

The server does not trust the persistent connection alone. ClaimRotation re-validates the daemon's OAuth access token on the request (guarantee EligibleClaimsOnly), so an expired or revoked credential cannot claim even if its socket still looks up.

Job-bound cipher writes

There is no separate nonce or write token. AcceptCipherUpdate authorises a write only against a RotationJob that is claimed by this daemon for the attempt's cipher (guarantee JobBoundWrite). Anything stale or mis-owned hits RejectCipherUpdate.

API-scoped reads & zero-knowledge

The credential has no general cipher-read scope (ApiScopedReads): the server serves only the cipher being actively rotated. The org key is delivered encrypted and decrypted locally with encryption_key (never transmitted); the server stores only ciphertext (ServerZeroKnowledge).

Eligibility = the security boundary

A daemon may claim a job only for a target it is enrolled, connected and assigned to (DaemonTargetAssignment). The assignment is the explicit reachability/security boundary; many daemons can be assigned one target for HA, and first claim wins.

Audit emission

Every rotation attempt and outcome emits RotationAudited — a pure sink (no rule chains off it). Durable WORM storage is the existing Phase-1 audit log's job, out of scope here. Outcomes:

Session termination — best-effort and decoupled

After a successful rotation, if terminate_sessions was requested:

  • Supported → a SessionTermination task runs with its own retry counter; failure abandons the task (MarkSessionTerminationAbandoned) without touching the rotation.
  • Unsupported → SessionTerminationUnsupported surfaces a warning to the server rather than failing the attempt.

The rotation succeeds the moment the password is rotated and the cipher synced — termination is never on that critical path.

Two distinct retry layers

Daemon: local transient retry

Inside one attempt, transient faults (a network blip, a momentary target/API error) are retried in place up to max_retry_attempts (5) with a retry_base_delay backoff, inside ExecuteRotation. RotationAttemptFailed is emitted only once these are exhausted (or the error is plainly non-transient).

Server: attempt-level retry

A hard failure that survives local retries is reported up; the server makes the job claimable again for a fresh attempt (RetryJob) until max_attempts (5) attempts have failed, then FailJob. Each attempt starts from a fresh password.

The two budgets are separate config values (both default 5) on different specs. The local one absorbs glitches cheaply; the server one is the outer round-trip for genuine failures and lets a struggling daemon fail over to another assigned one for free.

7Open questions

Things the specs explicitly leave undecided, in plain language. Daemon-side first, then server-side.

Daemon spec

Read blast radius (residual) deferred
The org key the daemon holds is still the theoretical crypto blast radius — a daemon compromise plus an API-authorisation bypass would expose the whole org vault. Closing it at the crypto layer needs per-cipher item keys (delivered per attempt, job-bound) or a write-only asymmetric scheme; both depend on Bitwarden per-item cipher keys.
Cipher write granularity deferred
With no partial-content API, rotation re-PUTs the whole cipher, so the in-flight job authorises replacing the entire object and requires a read-before-write. A dedicated partial-update/rotate endpoint would remove the read and tighten write scope to the password field; a separate bearer write-token would add defence in depth against an ownership-check bug.
Credential re-issuance
Once a daemon's credential is revoked, the session is terminal. How is a replacement credential provisioned and delivered to the daemon? (Referenced by the terminal refused/revoked states.)
Custom-script result format
How does a custom_script integration report its result — exit code, stdout parsing, or structured output? The spec leans toward exit code as simplest and most portable.

Server spec

Failure handling (§6.8)
FailJob and JobTimesOut currently reschedule to a near-term retry and emit RotationFailed as the seam. §6.8 should define the real policy — alerting and auto-disable after a threshold — and own next_rotation_at on terminal failure.
Collection-wide settings deferred
Applying one set of rotation settings across every credential in a collection at once. Deferred to keep Phase 1 per-credential; the per-credential UpdateRotationSettings path stands in.
Non-cron cadences
Schedule carries a cron expression. Do interval presets ("every 90 days") need a separate representation, or are all presets expressible as cron?
Rotation throttling
Many credentials on one target coming due together could hammer that target. Not modelled (no fleet-scale deployment assumed); if needed, throttle in the daemon/connector rather than the server scheduler.
Unroutable-job escalation
A job that stays pending because no eligible daemon is connected/assigned waits until JobTimesOut. Past a threshold it should escalate to an operator; delivery shares the unspecified alerting seam.
Daemon connectivity edges
Reconcile which daemon-side transitions (ServerConnection/DaemonSession) raise the server's DaemonConnected/DaemonDisconnected edges — in particular whether a session expiry that is not a transport drop counts as disconnected for claim eligibility.
Cancel-in-flight
Should disabling a target, pausing a config, applying new settings, or unassigning a daemon cancel a claimed job, or only stop new ones being offered? Today all four only stop new ones.
Manual-obligation escalation
Beyond surfacing awaiting_manual_rotation, should a manual obligation unmet past a threshold escalate — notify, flag severity, or raise an alert?
Access-event emitter binding
Which upstream systems wire into AccessGrantEnded (PAM leases, AAP grants, …)? The signal shape is resolved (it carries only the cipher); the concrete set of emitters and how they register is still open.
On-demand actor attribution
On-demand and access-triggered jobs record a source but not the triggering admin (only manual_recorded carries an actor). Should the audit attribute the on-demand actor end to end?
Method switching
Can an admin move a target between automatic and manual after creation (and supply/clear kind, policy, termination capability), and what happens to its configs' schedules and any active jobs? ManualConfigNeverJobbed assumes method is fixed at creation.
Secrets Manager support Phase 1 non-goal
A future config would point at an SM secret rather than a daemon/Cipher. Confirm the offer/claim/recovery/scheduling/audit machinery carries an SM rotation unchanged, and decide whether to generalise the cipher seam or add a parallel SM config.

8User-story scenarios

Read each scenario, think it through, then reveal the spec-accurate answer with the rules involved.

Recovery
A daemon claims a job, starts rotating, and then its connection drops before it reports any outcome. What happens to the job — and is this counted as a failed attempt?
The claim is released; it is not charged against the retry budget.

The server sees the drop and runs DaemonConnectionDropsReleaseJobs, which fires ReleaseJob only for jobs claimed_by that daemon. The job goes back to pending, claimed_by is cleared, and crucially attempt_count is decremented — losing connectivity is not a real attempt failure. After a backoff any connected, assigned daemon (or the same one on reconnect) re-claims it. The job_ttl deadline still backstops via JobTimesOut.

Rules: DaemonConnectionDropsReleaseJobs · ReleaseJob · (audit: released) · JobTimesOut (backstop)
Retry
An attempt fails with a genuine error (the target rejected the new password). The job is on attempt 2 of a max of 5. What does the server do next, and what does the next attempt look like?
The job becomes claimable again for a fresh, independent attempt.

The daemon's RotationAttempt transitions to failed (MarkAttemptFailed). Since attempt_count < max_attempts, the server runs RetryJob: job → pending, claimed_by cleared, next_claimable_at pushed out by a backoff, audit attempt_failed (with the reason). The next eligible daemon to claim makes a brand-new attempt starting from a freshly generated password — it could be the same daemon or another assigned one (free fail-over).

Rules: MarkAttemptFailed (daemon) · RetryJob (server) · ClaimRotation (re-claim)
Exhaustion
The 5th attempt fails. The retry budget is now exhausted. What state does the job reach, and what else happens to the configuration?
The job fails terminally and the config is rescheduled to a near-term retry.

With attempt_count >= max_attempts, FailJob fires: job → failed (terminal), next_rotation_at set to now + failure_retry_delay (1 hour), audit failed, and RotationFailed is emitted as the seam for the not-yet-specified §6.8 failure-handling policy (alerting / auto-disable). The near-term reschedule keeps the credential live until §6.8 lands.

Rules: FailJob · RotationFailed (seam) · open question §6.8
Routing
A scheduled rotation becomes due, but no daemon assigned to that target is currently connected. The job sits unclaimed. What ultimately happens?
It waits as pending, then times out at the deadline.

OfferRotation created the job pending and the server push-notified eligible daemons — but with none connected/assigned it simply waits. The moment one connects or is assigned it can be claimed (no re-offer needed, the job is already pending). If nothing claims it before created_at + job_ttl, JobTimesOut declares it timed_out, reschedules the config, and emits RotationFailed. (Escalating an unroutable job sooner is an open question.)

Rules: OfferRotation · ClaimRotation (when a daemon appears) · JobTimesOut · open question: unroutable-job escalation
Auth
A daemon connects and presents a credential the server rejects (wrong or revoked secret). Does the daemon keep retrying the connection?
No — the connection is terminally refused.

On connect, DaemonConnects creates a DaemonSession in authenticating. The rejection arrives as AuthenticationRejected; HandleAuthenticationRejected sets the session revoked and emits ConnectionRefused, so RefuseConnection drives the ServerConnection to refused — a terminal state. Unlike a transient drop (which Reconnect retries with backoff), the daemon does not reconnect, because re-presenting a rejected credential would loop forever. A replacement credential must be provisioned (open question).

Rules: HandleAuthenticationRejected · RefuseConnection · (contrast: Reconnect) · open question: credential re-issuance
Admin action
An admin disables a target system while one of its jobs is already claimed and executing on a daemon. What happens to that in-flight job, and to future rotations?
The in-flight claimed job runs to completion; only new rotations are stopped.

DisableTargetSystem sets the target disabled. OfferRotation requires target_system.status = active, so no new job is created while disabled — but jobs already claimed are explicitly unaffected and finish normally. Whether disabling should also cancel a claimed job is the cancel-in-flight open question (today it does not).

Rules: DisableTargetSystem · OfferRotation (guard) · open question: cancel-in-flight
Manual fallback
A credential on a manual-method target reaches its scheduled time. Does a daemon get dispatched? How is the rotation handled?
No daemon is dispatched — it becomes an admin obligation to record.

RotationDue requires method = automatic, so it never fires for a manual config — and ManualConfigNeverJobbed guarantees a manual config is never jobbed at all. Instead the config's awaiting_manual_rotation flag becomes true and is surfaced to the admin. After rotating out of band, the admin runs RecordManualRotation, which sets last_rotation_at, reschedules next_rotation_at, and writes an audit (manual_recorded, with actor) — exactly as a successful auto rotation would.

Rules: RotationDue (guard) · ManualConfigNeverJobbed (invariant) · RecordManualRotation
Session termination
A rotation succeeds and terminate_sessions was requested — but the target system can't terminate sessions. Does the attempt fail?
No. The attempt still succeeds; a warning is surfaced.

In HandleRotationSucceeded, when terminate_sessions is true but supports_session_termination is false, the daemon emits SessionTerminationUnsupported to the server rather than creating a SessionTermination task — termination is best-effort and decoupled, so the attempt is succeeded the moment the password is rotated and the cipher synced. (If it were supported, a SessionTermination task would run with its own independent retry counter.)

Rules: HandleRotationSucceeded → SessionTerminationUnsupported · (vs SessionTermination + RetrySessionTermination)
Stale write
A daemon's claim was released after a brief drop and another daemon re-claimed the job. The original daemon comes back and submits its (now stale) cipher write. Is it accepted?
No — it is rejected, because the job is no longer claimed by that daemon.

Cipher writes are authorised by the job itself, not a token. AcceptCipherUpdate requires a job in claimed status whose claimed_by equals the writer. After release/re-claim the claimed job belongs to a different daemon, so RejectCipherUpdate fires instead — audit write_rejected. The daemon surfaces this as a failed attempt (MarkAttemptFailed); if budget remains it becomes a fresh claimable attempt. The same rejection fences off late writes after a job has succeeded or timed out.

Rules: AcceptCipherUpdate (guard) · RejectCipherUpdate · MarkAttemptFailed · guarantee JobBoundWrite
Auth at claim time
A daemon's connection still looks up, but its access token has just expired. It tries to claim a newly offered job. Can it?
No — the claim is re-validated against the token, not just the socket.

ClaimRotation and the EligibleClaimsOnly guarantee require the claimant be enrolled, connected, assigned and presenting a valid OAuth access token tied to a still-active session. The server does not trust the persistent connection alone, so an expired token (or a revoked credential) is rejected at claim time. Daemon-side, the session would have gone expired (SessionExpires) and must re-authenticate via RefreshSession before claiming.

Rules: ClaimRotation (token re-validation) · EligibleClaimsOnly · SessionExpires · RefreshSession
Transient glitch
During rotation, the call to the target system fails once with a transient network blip, then would succeed on a retry. Does the server see an attempt failure?
No — the daemon absorbs it locally and never reports failure.

Inside ExecuteRotation the daemon retries a transient fault in place, up to max_retry_attempts (5) with a retry_base_delay backoff. RotationAttemptFailed is emitted only once these local retries are exhausted (or the error is plainly non-transient). A momentary blip costs no server round-trip, so the server never sees it — the attempt simply succeeds. This local retry is entirely distinct from the server's attempt-level RetryJob.

Rules: ExecuteRotation (local transient retry) · vs RetryJob (server attempt-level retry)
Concurrency
Two assigned daemons are notified of the same pending job and both try to claim it at the same moment. What happens?
First claim wins; the second finds it already claimed and fails.

ClaimRotation guards on job.status = pending. The first claim flips it to claimed and sets claimed_by; the second concurrent claim no longer sees a pending job and is rejected. This is how load-balancing emerges across an HA pool — whichever eligible daemon claims first does the work, and a busy daemon simply does not claim. (The invariant AtMostOneActiveJobPerConfig also keeps a single credential from rotating concurrently.)

Rules: ClaimRotation (pending guard, "first claim wins") · AtMostOneActiveJobPerConfig
