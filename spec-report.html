Specification Report

Bitwarden Credential Rotation

A connected daemon rotates credentials inside target systems on behalf of the Bitwarden server. The server schedules and dispatches rotation work as pull-based jobs; the daemon claims a job, executes one attempt, and writes the new (encrypted) password back into the vault cipher — all without the server ever holding a plaintext key or password.

rotation-server.allium — server side (owns scheduling, jobs, targets, config) rotation-daemon.allium — daemon side (executes one attempt, reports outcome) Layering: server uses daemon (one-way)

1Overview

Bitwarden manages secrets in an organization vault. This system keeps the credentials behind those secrets fresh by rotating them in the real target systems that own them — an Entra directory, a SQL Server account, or anything reachable by a custom script — and then writing the new password back into the matching vault Cipher.

End to end, a single rotation walks through eight steps — the server sets the work up and dispatches it, the daemon carries it out against the live system and proves it worked, and the server records the result:

Pull-based jobs

When a rotation becomes due the server publishes an available RotationJob. It does not push work at a daemon; an eligible daemon claims the job (a push nudge announces it — on creation, on daemon reconnect and on a late assignment). A retry is just a re-claim, and each claim is a time-bounded lease.

One attempt per claim

The server creates a RotationAttempt when a daemon claims a job. The daemon executes that one attempt from the claim's work snapshot and reports success or failure back by attempt_id. It owns no scheduling, no retry orchestration across attempts, and no target definitions.

Zero-knowledge writes

The daemon encrypts the new password with the organization key (delivered encrypted, decrypted locally) and the server stores only ciphertext. It never sees a plaintext password or key.

In one sentence

The server decides what rotates and when, hands the work to a daemon it trusts for that target, and the daemon does the rotation against the live system and writes the result back — authorised by the very job it claimed, with no separate write token and no plaintext crossing the server.

2The two sides and their boundary

The daemon and the server are two separate applications that run in tandem but are cleanly separated by an API. The daemon is a standalone app: it opens a connection to the server, authenticates, claims jobs and reports outcomes back — all over that link (a SignalR/WebSocket transport, modelled as ServerConnection with a DaemonSession riding on top). It never reaches into the server's internals; everything a rotation needs arrives on the claim as a self-contained work snapshot, so the daemon can act without calling back for more. That one-way flow is deliberate, and the two Allium specs mirror it: the server spec uses the daemon spec (use "./rotation-daemon.allium" as daemon) and references daemon types by qualified name (daemon/Cipher), but never the reverse.

Server owns

  • Target-system definitions (TargetSystem) — name, method, kind, password policy, status. No connection details.
  • Daemon identities & eligibility (DaemonRegistration, DaemonTargetAssignment, DaemonConnection).
  • Rotation configuration & triggers (RotationConfig, with an inline Schedule? + rotate_on_access_end).
  • Scheduling, dispatch, job tracking, retry orchestration, timeout, recovery (RotationJob) — and the claim lease (claimed_at + release_delay ⇒ execute_by).
  • Rotation attempts (RotationAttempt) — created on claim; their lifecycle and outcome, recorded from the daemon's report.
  • Cipher-write authorisation and audit emission — every operation, rotation and administrative alike (RotationAudited + AdministrationAudited).
  • The §6.8 failure policy: operator alerting and auto-pause after consecutive failures (the pure-sink OperatorAlertRaised).

Daemon owns

  • The transport link (ServerConnection) and authenticated session (DaemonSession).
  • Executing one try from the claim's work snapshot for the kind carried on the claim. It holds no attempt entity — the attempt is server-owned; it works only from the snapshot and reports the outcome by attempt_id.
  • Resolving connection details via the env-first CredentialResolver, keyed by target_system_id (Secrets Manager and local config are pluggable, opt-in resolvers).
  • Generating a policy-compliant password, verifying the rotated credential against the target system, and writing back the encrypted cipher.
  • Best-effort session termination as a sub-step of the attempt (its own local retry budget) and local transient retry.
  • The step-boundary abort discipline: never initiating a target-side step past session loss or the claim's execute_by lease (guarantee NoTargetActionPastSessionLoss).

Daemon-owned

No attempt or termination entity

The daemon holds no RotationAttempt and no session-termination entity of its own — both are server-side now (the attempt is the server's RotationAttempt; session termination is folded into it). The daemon works entirely from the self-contained RotationClaimed work snapshot (attempt_id, target details, password policy, cipher, account identity, terminate flag, and the claim's execute_by lease deadline) and reports the outcome back by attempt_id — a success via RotationSucceeded(attempt_id, session_termination), a failure via RotationAttemptFailed(attempt_id, reason, sync_state), relayed to the server as ReportRotationFailed(reporter, attempt_id, failure_reason, sync_state).

Session termination — folded into the attempt

No longer a separate stateful entity. Session termination is a guidance-level sub-step of executing the rotation (daemon-side), with its own local retry budget. Its result is reported as the session_termination field on the success report and recorded on RotationAttempt.session_termination as a SessionTerminationOutcome: not_requested / terminated / term_failed. It never fails or re-runs the rotation.

6Cross-cutting topics

Authentication & authorisation

OAuth client-credentials

The daemon authenticates with a provisioned DaemonCredential (client_id + client_secret), exchanged for a short-lived bearer access token (DaemonConnects → HandleAuthenticationSucceeded). Borrows Secrets Manager's token pattern.

Claim-time token re-validation

The server does not trust the persistent connection alone. ClaimRotation re-validates the daemon's OAuth access token on the request (guarantee EligibleClaimsOnly), so an expired or revoked credential cannot claim even if its socket still looks up.

Job-bound cipher writes

There is no separate nonce or write token. AcceptCipherUpdate authorises a write only against a RotationJob that is claimed by this daemon for the attempt's cipher (guarantee JobBoundWrite). Anything stale or mis-owned hits RejectCipherUpdate.

API-scoped reads & zero-knowledge

The credential has no general cipher-read scope (ApiScopedReads): the server serves only the cipher being actively rotated. The org key is delivered encrypted and decrypted locally with encryption_key (never transmitted); the server stores only ciphertext (ServerZeroKnowledge).

Re-issue vs revoke

A compromised credential is rotated in place: ReissueDaemonCredential generates a fresh client_secret + encryption_key, re-wraps the org key, invalidates the live session and shows the new token once (out of band) — registration identity, assignments and audit continuity survive. RevokeDaemon remains permanent decommission (recovery = a new registration, by design) and doubles as the in-flight brake for a runaway daemon.

Transport-only liveness

DaemonConnected/DaemonDisconnected map exclusively to the authenticated transport coming up/down — never to session state. A token expiring while the socket stays up is not a disconnect (that would release a healthy daemon's job mid-refresh); a rejected refresh or a revocation closes the transport, and that raises disconnected.

Eligibility = the security boundary

A daemon may claim a job only for a target it is enrolled, connected and assigned to (DaemonTargetAssignment). The assignment is the explicit reachability/security boundary; many daemons can be assigned one target for HA, and first claim wins.

In-flight safety — the claim lease and the step-boundary abort

The claim-release race at the target system is closed by two halves, one per side of the boundary. The cipher write was always fenced (JobBoundWrite); these fence the target system too:

Server half: the claim is a lease

ClaimRotation stamps claimed_at; the derived execute_by = claimed_at + release_delay (15 min, a dedicated recovery knob — placeholder tunable, sized to a worst-case single attempt and deliberately distinct from the 1-second retry_base_delay, which was the bug for release) rides to the daemon on the claim snapshot. ReleaseJob sets next_claimable_at to that lease expiry, so a dropped daemon's job never re-opens while the dropped daemon might still be inside its lease acting on the target. Clock skew is absorbed by the sizing margin. RetryJob is unchanged: a genuine failure reported by a live daemon still spaces on retry_base_delay.

Daemon half: abort at step boundaries

Guarantee NoTargetActionPastSessionLoss: the daemon never initiates a target-side step (target update, verify, session termination) unless its session is usable and execute_by has not passed. On transport loss, a terminal session (revoked/closed) or a lapsed lease it aborts at the current step boundary — never mid-API-call. The aborted attempt goes unreported (a report needs a session); the server's existing ReleaseJob/JobTimesOut machinery abandons it. A session merely expired with a refresh in flight is not loss — the daemon pauses at the boundary and continues in place.

Claimed jobs are never cancelled

Pausing a config, disabling a target, unassigning a daemon or changing settings only stops new offers and claims (a still-pending job is also held un-claimable by is_claimable). None of them cancels a claimed job: the daemon may already have reset the target-side password, and refusing its cipher write would manufacture the vault-stale state the system exists to prevent — the write must be allowed to land.

The emergency brake is RevokeDaemon

Revoking closes the daemon's transport; the daemon observes session loss and aborts at its next step boundary, and the closed transport flips its DaemonConnection disconnected, releasing the claimed job under the lease. Staleness risk on the target is consciously accepted when firing a daemon. Two smaller guards complete the picture: executing with no active session at all (the claim-to-start gap) fails fast with target_unchanged instead of wedging until job_ttl (ExecuteRotationWithoutSession), and a routine token expiry mid-rotation is absorbed by the local retry loop while the session refreshes — it never fails an attempt (that would wrongly spend the server retry budget); only a rejected refresh ends execution.

Verification and the failure sync-state

Step 4 of ExecuteRotation verifies the rotation: the daemon confirms via the kind integration that the account now authenticates with the new password (e.g. an authentication probe — the per-kind mechanics are an open question). The rotation is not treated as succeeded until verification passes. Guarantee VerifiedBeforeSuccess: a rotation is reported succeeded only after the new credential has been verified against the target system and the cipher write has been accepted — an unverified change is never reported as success. The server independently enforces the write half: RotationAttempt.cipher_updated is set only by AcceptCipherUpdate, and RecordRotationSucceeded refuses a success report without it (audited report_rejected) — a buggy daemon reporting success without writing cannot leave a succeeded job over a stale vault.

A failure that survives the daemon's local retries carries the vault↔target sync_state it left behind (FailureSyncState, recorded on the errored attempt and audited):

  • target_unchanged — the target was not modified; the stored cipher still matches it (a failure in steps 1–3 with the update known not to have applied).
  • target_updated — the target was changed but the cipher was not updated: the stored credential is stale until a later attempt or rotation converges (a failure after the target changed — verification, step 4, or the cipher write, step 5).
  • indeterminate — the daemon cannot tell whether the change applied (e.g. a timeout after submission).

Each attempt is independent and starts fresh: a new password is generated and both the target and the cipher are updated together, so a previous attempt's partial failure is converged by the next success — sync_state records the interim divergence. What makes that convergence sound is now an explicit guarantee, RotationByAdministrativeReset: every integration rotates by administrative reset — no step of a rotation may depend on the current credential value (the integration authenticates with resolver-supplied service credentials, never with the password being rotated). After a target_updated failure the next attempt's independently generated password can still be applied; a custom script doing a change-password rather than a reset would break this and must honour the constraint too.

Session termination — folded into the attempt

Session termination is no longer a separate entity. It is a guidance-level sub-step of executing the rotation (ExecuteRotation), run only after the rotation has already succeeded and only when terminate_sessions is set:

  • It has its own local retry loop using the daemon's max_retry_attempts / retry_base_delay budget — entirely the daemon's, mirroring the transient-step retry.
  • Its outcome rides on the success report's session_termination field and is recorded on RotationAttempt.session_termination as a SessionTerminationOutcome: not_requested (none asked for) / terminated (succeeded) / term_failed (its local retries exhausted).
  • It never fails or re-runs the rotation (guarantee TerminationNeverFailsRotation).
  • As a target-side step it honours the step-boundary abort discipline: if the session is lost or execute_by passes before it starts, it is simply not initiated (the rotation had already succeeded).
  • "Requested but unsupported" is impossible: CreateRotationConfig (and UpdateRotationAccount) validates terminate_sessions against the target's supports_session_termination at config time, so the capability flag is no longer even sent to the daemon.

The rotation succeeds the moment the password is rotated, verified and the cipher synced (guarantee TerminationNeverFailsRotation) — termination is never on that critical path.

Two distinct retry layers

Daemon: local transient retry

Inside one try, transient faults (a network blip, a momentary target/API error) are retried in place up to max_retry_attempts (5) with a retry_base_delay backoff, inside ExecuteRotation. The best-effort session-termination sub-step uses the same local budget on its own loop. RotationAttemptFailed is emitted only once these are exhausted (or the error is plainly non-transient), carrying the vault↔target sync_state the failure left behind.

Server: attempt-level re-claim

A hard failure that survives local retries is reported up; the server records the attempt errored and makes the job claimable again for a fresh attempt (RetryJob) until max_attempts (5) errored attempts have accrued (failed_attempts), then FailJob. Each fresh claim creates a new attempt and starts from a fresh password.

The two budgets are separate config values (both default 5) on different specs. The local one absorbs glitches cheaply; the server one is the outer round-trip for genuine failures and lets a struggling daemon fail over to another assigned one for free. A token expiring mid-rotation is deliberately in the local bucket: the daemon refreshes in place and continues, because charging routine housekeeping to the server's max_attempts budget would be wrong. And neither budget governs a daemon drop — that is the claim lease's job (release_delay, 15 min): a released job waits out the dropped claim's execute_by, not a retry backoff.

Failure policy (§6.8) — alerts and auto-pause

Formerly an open question, now specified. RotationFailed (emitted by FailJob and JobTimesOut) stays the seam; everything chains from it and ends at the pure-sink OperatorAlertRaised(kind, rotation_config, severity, reason) — like the audit sinks, no rule chains off it, and delivery mechanics (email, in-product, paging) are deliberately out of scope, exactly as audit persistence is.

Every terminal failure raises an alert

AlertOnRotationFailed passes the emit-site alert_kind through — job_failed (budget exhausted), job_unroutable (timed out with zero attempts: no eligible daemon was ever connected/assigned) or job_stuck (timed out while claimed) — and owns the severity policy: alert_elevated when sync_state = target_updated (the vault now holds a dead credential) or source = access_end (a security-mandated rotation did not happen); otherwise alert_normal.

Auto-pause after consecutive failures

RotationConfig.consecutive_failures is incremented on each terminal failure or timeout and reset by a success or a recorded manual rotation. At max_consecutive_failures (3, a placeholder tunable) AutoPauseAfterConsecutiveFailures pauses the config — never the target (a shared target keeps serving its other configs) — audits auto_paused and raises an elevated alert. This is what takes ownership of next_rotation_at on terminal failure: the failure_retry_delay (1 h) reschedule stands until auto-pause, after which a paused config's RotationDue cannot fire — ending the retry loop. Recovery is the ordinary admin ResumeRotation.

Overdue manual obligations escalate too

AlertManualObligationOverdue raises an elevated alert (manual_obligation_overdue) once a manual config's obligation has stood unmet past manual_obligation_alert_after (24 h, a placeholder tunable). manual_obligation_alerted is the re-fire brake — a temporal trigger that changes no state would re-fire forever — and is reset whenever the obligation is cleared (RecordManualRotation) or a fresh one is raised, so each new obligation re-arms the alert.

Dropped triggers & catch-up — events are never lost, schedules may skip

The organising principle, applied consistently across pause/resume and disable/enable: an event trigger (an access grant ending — security-relevant, unrepeatable) must never be lost; a schedule may skip missed windows; and an on-demand trigger is deliberately not latched — an admin can simply re-issue it.

  • Latch: an access-end for an automatic config that cannot be offered right now (config paused, or target disabled) sets pending_access_end and audits access_end_deferred (DeferAccessEndWhileUnavailable — its guard is the exact complement of RotateOnAccessEnd's, so an automatic access-end is either offered now or deferred, never dropped). A paused manual config latches likewise (DeferManualAccessEndWhilePaused); an enabled manual config has its obligation pulled due on the spot (RaiseManualObligationOnAccessEnd, audit manual_rotation_due).
  • Discharge: on ResumeRotation or EnableTargetSystem the latch is discharged exactly once — an automatic config gets a deferred OfferRotation with source: access_end; a manual config has next_rotation_at pulled to now.
  • Schedule catch-up: EnableTargetSystem now recomputes next_rotation_at from now for each automatic config with a schedule, mirroring resume — missed windows are intentionally skipped, never fired as a backlog. And ResumeRotation never erases an already-due manual obligation: a manual config that owes one keeps next_rotation_at at now instead of recomputing past it.

One residual gap is a live open question: an access-end arriving while the config is enabled, its target active and a job already in flight currently fires neither the offer nor the defer rule (see §7).

7Open questions & resolutions

What the specs still leave undecided, in plain language — and what the latest revision settled. Still-open questions first (daemon-side, then server-side), then the resolved ones, each with a short statement of the decision.

Still open — daemon spec

Read blast radius (residual) deferred
The org key the daemon holds is still the theoretical crypto blast radius — a daemon compromise plus an API-authorisation bypass would expose the whole org vault. Closing it at the crypto layer needs per-cipher item keys (delivered per attempt, job-bound) or a write-only asymmetric scheme; both depend on Bitwarden per-item cipher keys.
Cipher write granularity deferred
With no partial-content API, rotation re-PUTs the whole cipher, so the in-flight job authorises replacing the entire object and requires a read-before-write. A dedicated partial-update/rotate endpoint would remove the read and tighten write scope to the password field; a separate bearer write-token would add defence in depth against an ownership-check bug.
Custom-script result format
How does a custom_script integration report its result — exit code, stdout parsing, or structured output? The spec leans toward exit code as simplest and most portable. (A custom script must also honour RotationByAdministrativeReset — a change-password script that needs the old password would make a target_updated failure unrecoverable.)
Verification mechanics per kind
Step 4 of ExecuteRotation verifies the rotated credential before the rotation is reported succeeded. MSSQL can probe by opening a connection as the rotated login; Entra may not permit a plain password probe (MFA / conditional access can block it) and may need a directory-level confirmation instead; a custom script needs a verify operation in its contract. What does verification concretely mean for each kind — and may a kind opt out?
Credential resolver precedence
The default CredentialResolver is environment variables, with Bitwarden Secrets Manager and a local config file as pluggable, opt-in resolvers. When more than one is configured, what is the precedence — and is it per-target or daemon-wide? The resolver encapsulates the lookup; the precedence policy is not yet pinned down.

Still open — server spec

account_identity integrity (server-tamper resistance) deferred
account_identity is stored server-side in plaintext on RotationConfig and carried verbatim to the daemon on the claim (RotationClaimed), where it picks which target-system account is rotated and session-terminated. A compromised or malicious server could substitute a different account_identity, pointing the daemon's privileged operations at an account the admin never chose. Encrypting/authenticating it client-side under the org key when the admin saves the config (exactly as vault ciphers are, so the server stores ciphertext it can neither read nor forge) would let the daemon detect substitution on the claim — extending ServerZeroKnowledge from the password to the account identity, closed at the crypto layer like the Read-blast-radius question.
Lease-bound least-privilege daemon auth deferred
The daemon's client-credentials session (DaemonSession) carries broad standing authority to write vault ciphers; operations are scoped only after the fact by the claimed RotationJob (JobBoundWrite) and ApiScopedReads. Hardening: carry a lease-id on the job (from the upstream grant — a PAM lease, see RotateOnAccessEnd) and have the server grant only the strictly-needed endpoints when the daemon presents a lease-id that is due for rotation and matches the target cipher — turning standing authority into a per-lease capability, so a stolen credential with no live, due lease grants nothing (defence in depth beyond JobBoundWrite/ApiScopedReads). Open whether it generalises to scheduled/on-demand jobs (no upstream lease) or applies only to access-end jobs.
Collection-wide settings deferred
Applying one set of rotation triggers across every managed credential in a collection at once. Deferred to keep Phase 1 per-credential; the per-credential UpdateRotationSettings path stands in. Revisit with the collection-membership resolution it needs.
Non-cron cadences
Schedule carries a cron expression. Do interval presets ("every 90 days") need a separate representation, or are all presets expressible as cron?
Rotation throttling
Many credentials on one target coming due together could hammer that target. Not modelled (no fleet-scale deployment assumed); if needed, throttle in the daemon/connector rather than the server scheduler.
Access-event emitter binding
Which upstream systems wire into AccessGrantEnded (PAM leases, AAP grants, …)? The signal shape is resolved (it carries only the cipher); the concrete set of emitters and how they register is still open.
On-demand actor attribution
On-demand and access-triggered jobs record a source but not the triggering admin (settings_updated, paused, resumed and manual_recorded carry an actor; the job-derived outcomes do not). Should the audit attribute the on-demand actor end to end?
Cipher-level "last rotated" display
Should the vault UI show a last-rotated timestamp on the cipher itself, derived by querying the audit log for rotation events (the audit log being the authoritative record that a rotation happened), rather than a field the rotation machinery maintains? RotationConfig.last_rotation_at exists server-side; this question is about surfacing rotation history on the cipher.
Access-end during an active job is silently dropped new deferred
RotateOnAccessEnd requires no active job, and DeferAccessEndWhileUnavailable's guard (paused, or target disabled) is the exact complement only over enabled × target-status — it does not cover the has_active_job case. So an AccessGrantEnded arriving while an automatic config is enabled, its target active and a job pending or claimed fires neither rule: the event is lost, against the "an event trigger must never be lost" principle. The in-flight job does not necessarily satisfy the access-end intent — its password may have been generated before the grant ended, and it may yet fail terminally. Candidate resolutions: (a) latch pending_access_end here too and discharge it when the active job resolves; or (b) document the drop as deliberate on the grounds that the concurrent rotation satisfies the intent. (Manual configs are unaffected — they never have jobs.)
Method switching
Can an admin move a target between automatic and manual after creation (and supply/clear kind, policy, termination capability), and what happens to its configs' schedules and any active jobs? ManualConfigNeverJobbed assumes method is fixed at creation. (UpdateTargetSystemPolicy now edits the policy and termination capability, but kind — and method — stay deliberately immutable: existing account identities are interpreted by the kind.)
Secrets Manager support Phase 1 non-goal
A future config would point at an SM secret rather than a daemon/Cipher. Confirm the offer/claim/recovery/scheduling/audit machinery carries an SM rotation unchanged, and decide whether to generalise the cipher seam or add a parallel SM config.

Failure handling (§6.8) → alerts + auto-pause specified resolved
RotationFailed stays the seam. AlertOnRotationFailed raises the pure-sink OperatorAlertRaised on every terminal failure/timeout — severity elevated when sync_state = target_updated (the vault holds a dead credential) or source = access_end (a security-mandated rotation did not happen). consecutive_failures accrues per terminal failure/timeout and at max_consecutive_failures (3) the config — never the target — auto-pauses (audit auto_paused, elevated alert). §6.8 thereby owns next_rotation_at on terminal failure. Alert delivery stays out of scope.
Unroutable-job escalation → folded into §6.8 resolved
JobTimesOut now distinguishes job_unroutable (timed out with zero attempts — no eligible daemon was ever connected/assigned) from job_stuck (timed out while claimed) via the alert_kind on RotationFailed, and the operator alert rides the shared OperatorAlertRaised seam.
Manual-obligation escalation → AlertManualObligationOverdue resolved
An elevated manual_obligation_overdue alert fires once a manual config's obligation stands unmet past manual_obligation_alert_after (24 h). manual_obligation_alerted is the re-fire brake, reset when the obligation is cleared or a fresh one is raised, so each new obligation re-arms the alert.
Daemon connectivity edges → transport-only resolved
DaemonConnected/DaemonDisconnected map exclusively to the authenticated transport coming up/down, never to session state. A session expiry with the transport up is not disconnected — flipping it would release a healthy daemon's job mid-refresh, and it is unnecessary for eligibility because ClaimRotation re-validates the OAuth token per claim. A rejected refresh or a revocation closes the transport, and that raises disconnected.
Cancel-in-flight → claimed jobs are never cancelled resolved
Pause, disable, unassign and settings changes only stop new offers and claims (a still-pending job is also held un-claimable). None cancels a claimed job: the daemon may already have reset the target-side password, and refusing its cipher write would manufacture the vault-stale state the system exists to prevent — the write must land. The emergency brake for a runaway daemon is RevokeDaemon, via the step-boundary abort.
Disabled-target catch-up & dropped triggers → events never lost, schedules may skip resolved
EnableTargetSystem now recomputes next_rotation_at from now (missed windows skipped, mirroring resume). An access-end that cannot be offered right now is latched on pending_access_end (audit access_end_deferred; DeferAccessEndWhileUnavailable / DeferManualAccessEndWhilePaused) and discharged on ResumeRotation/EnableTargetSystem — a deferred offer with source: access_end, or a manual obligation pulled due. ResumeRotation never erases an already-due manual obligation. On-demand triggers are deliberately not latched (an admin can re-issue). The residual has-active-job gap is the new open question above.

8User-story scenarios

Read each scenario, think it through, then reveal the spec-accurate answer with the rules involved.

Recovery
A daemon claims a job, starts rotating, and then its connection drops before it reports any outcome. What happens to the job — and is this counted as a failed attempt?
The claim is released; it is not charged against the retry budget — and the job stays locked until the dropped claim's lease elapses.

The server sees the drop and runs DaemonConnectionDropsReleaseJobs, which fires ReleaseJob only for jobs claimed_by that daemon. The job goes back to pending, claimed_by is cleared, and crucially the in-flight server-owned attempt is marked abandoned (AbandonAttempt) rather than errored — and failed_attempts counts only errored attempts, so losing connectivity is never charged to the budget. The job becomes re-claimable only at the dropped claim's execute_by (claimed_at + release_delay, 15 min — not the 1-second retry backoff), because the dropped daemon may still be mid-rotation against the target; daemon-side it aborts at its next step boundary and never acts past its own execute_by (NoTargetActionPastSessionLoss). Then any connected, assigned daemon (or the same one on reconnect) re-claims it for a fresh attempt. The expires_at deadline still backstops via JobTimesOut.

Rules: DaemonConnectionDropsReleaseJobs · ReleaseJob (lease: next_claimable_at = execute_by) · AbandonAttempt (attempt abandoned) · NoTargetActionPastSessionLoss (daemon abort) · (audit: released) · JobTimesOut (backstop)
Retry
An attempt fails with a genuine error (the target rejected the new password). The job is on attempt 2 of a max of 5. What does the server do next, and what does the next attempt look like?
The job becomes claimable again for a fresh, independent attempt.

The daemon reports the failure by attempt_id (ReportRotationFailed, carrying the reason and the vault↔target sync_state it left behind); the server transitions its own RotationAttempt to errored (RecordRotationFailed), recording both. The attempt's transition drives the job: since has_retry_budget still holds (failed_attempts.count < max_attempts), RetryJob fires: job → pending, claimed_by cleared, next_claimable_at pushed out by a backoff, audit attempt_failed (with the reason and sync_state). The next eligible daemon to claim makes a brand-new attempt (a new server-owned RotationAttempt) starting from a freshly generated password — it could be the same daemon or another assigned one (free fail-over).

Rules: ReportRotationFailed (daemon) · RecordRotationFailed → attempt errored · RetryJob (server) · ClaimRotation (re-claim)
Exhaustion
The 5th attempt fails. The retry budget is now exhausted. What state does the job reach, and what else happens to the configuration?
The job fails terminally, an operator alert is raised, and repeated terminal failures auto-pause the config.

When the daemon's failure report transitions the 5th attempt to errored, has_retry_budget no longer holds (failed_attempts.count >= max_attempts), so FailJob fires instead of RetryJob: job → failed (terminal), next_rotation_at set to now + failure_retry_delay (1 hour), consecutive_failures incremented, audit failed, and RotationFailed is emitted as the §6.8 seam. From it, AlertOnRotationFailed raises OperatorAlertRaised (job_failed) — elevated if the last attempt's sync_state is target_updated (the vault now holds a dead credential) or the rotation was access_end-mandated. At max_consecutive_failures (3) consecutive terminal failures, AutoPauseAfterConsecutiveFailures pauses the config (never the target), audits auto_paused and alerts — ending the hourly retry loop until an admin resumes. A success (or recorded manual rotation) resets the count. Only errored attempts count toward the budget — abandoned ones are not.

Rules: RecordRotationFailed → attempt errored · FailJob (consecutive_failures + 1) · RotationFailed (seam) · AlertOnRotationFailed → OperatorAlertRaised · AutoPauseAfterConsecutiveFailures (audit: auto_paused)
Routing
A scheduled rotation becomes due, but no daemon assigned to that target is currently connected. The job sits unclaimed. What ultimately happens?
It waits as pending, then times out at the deadline — flagged to an operator as unroutable.

OfferRotation created the job pending and the server push-notified eligible daemons — and it is re-announced the moment a daemon connects (NotifyClaimableJobsOnConnect) or a late assignment lands (NotifyPendingJobsOnAssignment), so it can be claimed with no re-offer (the job is already pending). If nothing claims it before created_at + job_ttl, JobTimesOut declares it timed_out, reschedules the config, increments consecutive_failures and emits RotationFailed with alert_kind = job_unroutable (zero attempts — distinguished from a stuck claiming daemon, job_stuck), which AlertOnRotationFailed turns into an operator alert.

Rules: OfferRotation · NotifyClaimableJobsOnConnect / NotifyPendingJobsOnAssignment · ClaimRotation (when a daemon appears) · JobTimesOut (job_unroutable) · AlertOnRotationFailed → OperatorAlertRaised
Auth
A daemon connects and presents a credential the server rejects (wrong or revoked secret). Does the daemon keep retrying the connection?
No — the connection is terminally refused.

On connect, DaemonConnects creates a DaemonSession in authenticating. The rejection arrives as AuthenticationRejected; HandleAuthenticationRejected sets the session revoked and emits ConnectionRefused, so RefuseConnection drives the ServerConnection to refused — a terminal state. Unlike a transient drop (which Reconnect retries with backoff), the daemon does not reconnect, because re-presenting a rejected credential would loop forever. Recovery: the server reissues a credential in place (ReissueDaemonCredential — identity and assignments preserved, token shown once) and the operator restarts the daemon with the new token, which DaemonStarts permits after a terminal refusal.

Rules: HandleAuthenticationRejected · RefuseConnection · (contrast: Reconnect) · ReissueDaemonCredential · DaemonStarts (restart after refusal)
Admin action
An admin disables a target system while one of its jobs is already claimed and executing on a daemon. What happens to that in-flight job, and to future rotations?
The in-flight claimed job runs to completion — by design; only new rotations are stopped.

DisableTargetSystem sets the target disabled and audits it (AdministrationAudited: target_disabled). OfferRotation requires target_system.status = active, so no new job is created while disabled, and a still-pending job is held un-claimable (is_claimable). But a claimed job is deliberately never cancelled (resolved): the daemon may already have reset the target-side password, and refusing its cipher write would manufacture the vault-stale state the system exists to prevent — the write must land. (The emergency brake for a runaway daemon is RevokeDaemon.) Triggers are no longer silently dropped either: an access-end while disabled is latched (pending_access_end, audit access_end_deferred), and re-enabling recomputes schedules (missed windows skipped) and discharges the deferral.

Rules: DisableTargetSystem · AdministrationAudited (target_disabled) · OfferRotation / is_claimable (guards) · DeferAccessEndWhileUnavailable · EnableTargetSystem (catch-up) · resolved: cancel-in-flight
Manual fallback
A credential on a manual-method target reaches its scheduled time. Does a daemon get dispatched? How is the rotation handled?
No daemon is dispatched — it becomes an admin obligation to record.

RotationDue requires method = automatic, so it never fires for a manual config — and ManualConfigNeverJobbed guarantees a manual config is never jobbed at all. Instead the config's awaiting_manual_rotation flag becomes true and is surfaced to the admin. If the obligation stands unmet past manual_obligation_alert_after (24 h), AlertManualObligationOverdue raises an elevated operator alert (once — manual_obligation_alerted is the re-fire brake). After rotating out of band, the admin runs RecordManualRotation, which sets last_rotation_at, reschedules next_rotation_at, resets the alert brake and consecutive_failures, and writes an audit (manual_recorded, with actor) — exactly as a successful auto rotation would.

Rules: RotationDue (guard) · ManualConfigNeverJobbed (invariant) · AlertManualObligationOverdue (24 h) · RecordManualRotation
Session termination
A rotation succeeds and terminate_sessions was requested, but the termination call to the target keeps failing even after the daemon's local retries. Does the attempt fail?
No. The attempt is rotated; termination is reported as term_failed.

Session termination is folded into executing the rotation (ExecuteRotation), as a best-effort sub-step that runs only after the password is already rotated, verified and the cipher synced. It has its own local retry loop on the daemon's max_retry_attempts / retry_base_delay budget; once those are exhausted it gives up without ever re-running the rotation (guarantee TerminationNeverFailsRotation). The success report carries session_termination = term_failed, which the server records on RotationAttempt.session_termination. The "requested but unsupported" case can't even arise: CreateRotationConfig already validated terminate_sessions against the target's supports_session_termination at config time, so that flag is never even sent to the daemon.

Rules: ExecuteRotation (termination sub-step, own local retry) · RotationSucceeded(session_termination = term_failed) · RecordRotationSucceeded · guarantee TerminationNeverFailsRotation · CreateRotationConfig (config-time guard)
Verification
The daemon sets the new password in the target system successfully, but the verification step cannot confirm the account authenticates with it — even after the local retries. Is the rotation reported as succeeded, and what does the vault now hold?
No — it is a failed attempt with sync_state = target_updated, and the stored cipher is stale.

Step 4 of ExecuteRotation verifies the rotation via the kind integration before anything is reported; guarantee VerifiedBeforeSuccess says a rotation is reported succeeded only after the new credential is verified and the cipher write accepted — an unverified change is never a success. Here the target was already changed but the vault was not, so the daemon reports RotationAttemptFailed with target_updated: the stored credential is stale until a later attempt converges. The server records it on the errored attempt and it rides on the attempt_failed/failed audit outcomes; a fresh claim generates a fresh password and updates target and cipher together, converging the divergence. (What verification concretely means per kind is an open question.)

Rules: ExecuteRotation (step 4, verify) · RotationAttemptFailed(sync_state = target_updated) · RecordRotationFailed · RetryJob/FailJob (sync_state audited) · guarantee VerifiedBeforeSuccess · open question: verification mechanics per kind
Stale write
A daemon's claim was released after a brief drop and another daemon re-claimed the job. The original daemon comes back and submits its (now stale) cipher write. Is it accepted?
No — it is rejected, because the job is no longer claimed by that daemon.

Cipher writes are authorised by the job itself, not a token. AcceptCipherUpdate requires the referenced (server-owned) attempt to still be executing and its job in claimed status whose claimed_by equals the writer. After release/re-claim the original daemon's old attempt is already abandoned and the claimed job belongs to a different daemon, so RejectCipherUpdate fires instead — audit write_rejected. The daemon surfaces this as a failed attempt (ReportRotationFailed); if budget remains the job becomes claimable for a fresh attempt. The same rejection fences off late writes after a job has succeeded or timed out — and a late outcome report from the fenced-off daemon is likewise refused and audited (RejectStaleSuccessReport / RejectStaleFailureReport: report_rejected). Note the re-claim itself could only have happened after the original claim's execute_by lease elapsed.

Rules: AcceptCipherUpdate (guard) · RejectCipherUpdate · RejectStaleSuccessReport / RejectStaleFailureReport · ReportRotationFailed · guarantee JobBoundWrite
Auth at claim time
A daemon's connection still looks up, but its access token has just expired. It tries to claim a newly offered job. Can it?
No — the claim is re-validated against the token, not just the socket.

ClaimRotation and the EligibleClaimsOnly guarantee require the claimant be enrolled, connected, assigned and presenting a valid OAuth access token tied to a still-active session. The server does not trust the persistent connection alone, so an expired token (or a revoked credential) is rejected at claim time. Daemon-side, the session would have gone expired (SessionExpires) and must re-authenticate via RefreshSession before claiming. Note the expiry does not mark the daemon disconnected server-side (the edges are transport-only) — its claimed jobs are not released mid-refresh; the per-claim token check is exactly what makes that safe.

Rules: ClaimRotation (token re-validation) · EligibleClaimsOnly · SessionExpires · RefreshSession · DaemonConnectivity (transport-only edges)
Transient glitch
During rotation, the call to the target system fails once with a transient network blip, then would succeed on a retry. Does the server see an attempt failure?
No — the daemon absorbs it locally and never reports failure.

Inside ExecuteRotation the daemon retries a transient fault in place, up to max_retry_attempts (5) with a retry_base_delay backoff. RotationAttemptFailed is emitted only once these local retries are exhausted (or the error is plainly non-transient). A momentary blip costs no server round-trip, so the server never sees it — the attempt simply succeeds. This local retry is entirely distinct from the server's attempt-level RetryJob.

Rules: ExecuteRotation (local transient retry) · vs RetryJob (server attempt-level retry)
Concurrency
Two assigned daemons are notified of the same pending job and both try to claim it at the same moment. What happens?
First claim wins; the second finds it already claimed and fails.

ClaimRotation guards on job.status = pending. The first claim flips it to claimed and sets claimed_by; the second concurrent claim no longer sees a pending job and is rejected. This is how load-balancing emerges across an HA pool — whichever eligible daemon claims first does the work, and a busy daemon simply does not claim. (The invariant AtMostOneActiveJobPerConfig also keeps a single credential from rotating concurrently.)

Rules: ClaimRotation (pending guard, "first claim wins") · AtMostOneActiveJobPerConfig
In-flight brake
An admin revokes a daemon (RevokeDaemon) while it is mid-rotation — it has already reset the target-side password but not yet written the cipher. What stops the daemon, and what happens to the job?
The revoke closes the transport; the daemon aborts at its next step boundary, and the job is abandoned and released under the lease.

Revoking is the deliberate in-flight brake (pause/disable/unassign never touch a claimed job). The server closes the daemon's transport; daemon-side the drop closes its session (ConnectionDropClosesSessions) and, per NoTargetActionPastSessionLoss, it never initiates the next target-side step — aborting at the step boundary, never mid-API-call. The attempt goes unreported (a report needs a session); server-side the closed transport flips the daemon disconnected, DaemonConnectionDropsReleaseJobs → ReleaseJob abandons the attempt (not charged) and the job re-opens only at the dropped claim's execute_by. The next claim's fresh, independently generated password converges the target-updated divergence — sound because no rotation step depends on the current credential value (RotationByAdministrativeReset). Staleness risk in the window is consciously accepted when firing a daemon.

Rules: RevokeDaemon · ConnectionDropClosesSessions · NoTargetActionPastSessionLoss (step-boundary abort) · DaemonConnectionDropsReleaseJobs · ReleaseJob (lease) · RotationByAdministrativeReset
Deferred trigger
A PAM lease over a managed credential ends while its rotation config is paused for a change freeze. The security-mandated rotation cannot be offered right now. Is the signal lost?
No — it is latched and discharged on resume. Event triggers are never lost.

DeferAccessEndWhileUnavailable fires (its guard is the exact complement of RotateOnAccessEnd's, so an automatic access-end is either offered now or deferred, never dropped): it latches pending_access_end and audits access_end_deferred, so the event leaves a trace immediately. On ResumeRotation the deferral is discharged as a fresh OfferRotation with source: access_end (on a manual config the obligation is pulled due instead). The same discharge runs on EnableTargetSystem for a disabled target. Contrast the schedule: windows missed during the pause are deliberately skipped on resume, and an on-demand trigger is deliberately not latched — an admin can re-issue it.

Rules: DeferAccessEndWhileUnavailable / DeferManualAccessEndWhilePaused · ResumeRotation / EnableTargetSystem (discharge) · audit: access_end_deferred · contrast: RotationDue (schedules skip)
Token expiry mid-rotation
A long rotation straddles the daemon's short-lived access token: it expires right as the daemon goes to write the cipher (the target is already updated and verified). Does the attempt fail with target_updated?
No — the daemon refreshes in place; token expiry never fails an attempt.

An expired token during a server-facing step is a transient: the local retry loop absorbs it while the existing SessionExpires → RefreshSession → active cycle completes (bounded by execute_by), and the attempt continues where it paused. Failing it would wrongly spend the server's max_attempts budget on routine housekeeping. The expiry also does not release the job — the server's connectivity edges are transport-only. Only a rejected refresh (the credential was revoked mid-rotation) ends execution: that is session loss, so the daemon aborts at the step boundary, the attempt goes unreported, and the server abandons it.

Rules: ExecuteRotation (refresh-in-place, local retry) · SessionExpires · RefreshSession · DaemonConnectivity (transport-only) · NoTargetActionPastSessionLoss (rejected refresh)
