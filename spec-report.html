1Overview

The Bitwarden Rotation Daemon is a service that automatically rotates credentials (passwords) for external systems — Microsoft Entra users, MSSQL accounts, or anything reachable by a custom script — on behalf of a Bitwarden organization. When it rotates a credential, it updates the account on the target system and writes the new password back into the Bitwarden vault cipher so it's always current.

The system is split across two spec files that form a clean boundary:

FileResponsibility
rotation-daemon.alliumThe daemon process: connects to the Bitwarden server, receives rotation tasks, executes them against target systems, writes the new password back to the vault.
rotation-server.alliumThe Bitwarden server side: registers target systems and daemon identities, manages rotation configurations and schedules, dispatches tasks, tracks execution, handles recovery, and emits the audit trail.
🔐
Zero-knowledge by design. The server never holds a plaintext organization key or plaintext password. The daemon decrypts the org key locally using a local encryption_key that is never transmitted. Every password written to the vault is ciphertext encrypted client-side. The server stores and forwards it without ever seeing the plaintext.

4State Machines

Six entities carry explicit status state machines. Understanding these is key to following any flow.

ServerConnection

The persistent connection between the daemon and the Bitwarden server. It is never terminal — a disconnection always triggers a reconnect attempt with exponential backoff.

ServerConnection status
stateDiagram-v2 direction LR [*] --> connecting connecting --> connected : auth succeeds\n(OpenConnection) connecting --> disconnected : auth rejected\n(RefuseConnection) connected --> disconnected : server interrupts\n(ServerInterruptsConnection) disconnected --> connecting : auto-reconnect\n(Reconnect, backoff)
ℹ
The connection becomes connected only once authentication succeeds — not at the TCP/WebSocket layer. This ensures the daemon never attempts task execution without a valid session.

DaemonSession

The daemon's authenticated session. One session is created per connection attempt. revoked is terminal: the daemon cannot reconnect until issued a new credential.

DaemonSession status
stateDiagram-v2 direction LR [*] --> authenticating : DaemonConnects authenticating --> active : HandleAuthenticationSucceeded authenticating --> revoked : HandleAuthenticationRejected active --> expired : SessionExpires\n(access token TTL lapses) active --> revoked : HandleSessionRevoked\n(admin revokes daemon) expired --> authenticating : RefreshSession\n(re-presents credential) revoked --> [*]

When active, the session holds three values: access_token, expires_at, and organization_key. The org key is derived by decrypting the server's response with the local encryption_key — the server never sees the plaintext.

RotationTask

One execution of a rotation, created by the server and executed by the daemon. Retries happen within executing — the task stays there until it succeeds or exhausts all attempts.

RotationTask status
stateDiagram-v2 direction LR [*] --> pending : PerformDispatch pending --> executing : TaskReceived executing --> executing : RetryRotation\n(attempt_count < 5) executing --> succeeded : HandleRotationSucceeded executing --> failed : MarkRotationFailed\n(retries exhausted) succeeded --> [*] failed --> [*]

TaskDispatch

The server-side mirror of a RotationTask. Tracks the task's progress and enables recovery. A dispatch can be lost if the connection drops while the task is in flight.

TaskDispatch status
stateDiagram-v2 direction LR [*] --> dispatched : PerformDispatch dispatched --> in_progress : MarkDispatchStarted\n(task → executing) dispatched --> lost : connection drops in_progress --> completed : MarkDispatchCompleted\n(task → succeeded) in_progress --> failed : MarkDispatchFailed\n(task → failed) in_progress --> lost : connection drops completed --> [*] failed --> [*] lost --> [*]
⚠
When a dispatch goes lost, its rotation config's next_rotation_at is set to now, so it becomes immediately due for re-dispatch on reconnect. No rotation is permanently lost across a connection drop.

DaemonConnection

The server's per-daemon record of connection liveness. One DaemonConnection is created per registered daemon (starting disconnected). The server flips it when the daemon's authenticated transport comes up or down. Routing and per-daemon recovery both read this — a daemon only receives dispatches while connected, and only its own in-flight dispatches are lost when it drops.

DaemonConnection status
stateDiagram-v2 direction LR [*] --> disconnected : InitDaemonConnection\n(on registration) disconnected --> connected : MarkDaemonConnected connected --> disconnected : MarkDaemonDisconnected\n(→ lose in-flight dispatches)

SessionTermination

Post-rotation cleanup: terminates active sessions for the rotated account. Completely independent of the rotation task — abandoned does not fail the rotation.

SessionTermination status

5Connection & Authentication

When the daemon starts, it immediately begins connecting. The connection only becomes usable once the daemon has authenticated and received an organization key it can use to encrypt vault writes.

Token expiry and refresh

Access tokens are short-lived. When session.expires_at ≤ now, the rule SessionExpires fires and transitions the session to expired, which immediately triggers RefreshSession to move it back to authenticating. The daemon re-presents its credential and gets a fresh token without admin intervention.

Revocation

An admin can revoke a daemon from the server UI. This triggers HandleSessionRevoked → session goes revoked (terminal). The server also closes the connection. The daemon cannot reconnect until issued a new DaemonCredential. (How re-issuance works is an open question — see §15.)

♾
Invariant: AtMostOneActiveSession — at any point at most one DaemonSession may be active. A refresh creates a new session in authenticating before the old one expires.

6Rotation Triggers

A rotation can be triggered in four ways. All four converge on a single choke point — PerformDispatch — that enforces all eligibility guards before creating a task.

How triggers converge on dispatch
flowchart TB T1["⏱ Scheduled\nRotationDue\n(next_rotation_at ≤ now)"] T2["👤 On-demand\nTriggerRotationNow\n(admin clicks 'Rotate now')"] T3["🔑 Access event\nRotateOnAccessEnd\n(PAM/AAP grant ended)"] T4["🔄 Reconnect recovery\nRedispatchOnReconnect\n(connection re-established)"] T5["📤 Queue drain\nDrainTargetQueue\n(target slot freed)"] DP["DispatchRotation(rotation_config, source)"] T1 --> DP T2 --> DP T3 --> DP T4 --> DP T5 --> DP PD{"PerformDispatch\nguards"} DP --> PD G1["✓ config.enabled"] G2["✓ mode = automatic"] G3["✓ no in-flight dispatch"] G4["✓ registration active"] G5["✓ target has capacity"] PD --> G1 PD --> G2 PD --> G3 PD --> G4 PD --> G5 G1 & G2 & G3 & G4 & G5 --> OUT["Create RotationTask\n+ TaskDispatch\n(routed to chosen daemon)"] style PD fill:#fff0e6,stroke:#a04000 style OUT fill:#e8f5ed,stroke:#1a7d3b

The four triggers explained

Scheduled (RotationDue). Fires as a temporal trigger when rotation_config.next_rotation_at ≤ now. Only fires when a schedule exists — a config with no schedule never has a next_rotation_at, so this trigger never fires for it.

On-demand (TriggerRotationNow). An admin triggers rotation immediately from the RotationConfigView surface. Useful for immediate need or testing. Only available for automatic-mode configs.

On access end (RotateOnAccessEnd). An upstream access-control system (PAM leasing, AAP, etc.) signals via AccessEventIntake that a grant over a managed credential has ended. The cipher alone identifies the config (one config per cipher). The config must have rotate_on_access_end = true.

Reconnect (RedispatchOnReconnect). On every reconnect, the server re-dispatches all due automatic configs. Combined with ConnectionDropsLoseDispatches (which makes in-flight configs immediately due), this recovers from connection drops. See §10 for the full recovery flow.

Manual configurations

Configs with mode = manual skip all triggers. When they become due, awaiting_manual_rotation is surfaced to administrators. The rotation is performed out-of-band and recorded via RecordManualRotation. See §12.

7Rotation Execution

Once the daemon receives a RotationTask, it executes a fixed sequence of steps. On any failure, the whole sequence restarts from step 1 — a fresh password is always generated so the target system and vault cipher stay in sync even after a partial failure.

advance schedule (next_rotation_at)

Retries

If any step fails, RotationAttemptFailed is raised. If attempt_count < max_retry_attempts (5), the rule RetryRotation increments the counter and re-emits ExecuteRotation after an exponential backoff delay (retry_base_delay × 2^(attempt_count − 1)).

When retries are exhausted, MarkRotationFailed marks the task failed. On the server side, MarkDispatchFailed reschedules the config to now + failure_retry_delay (1 hour) and emits RotationFailed as the seam for a future failure-handling policy (§6.8 — an open question).

⚠
Important: A failed rotation is not silently advanced to the next scheduled occurrence. It is rescheduled to a near-term retry window (1 hour) so it tries again soon. The schedule only advances on success.

8Cipher Write Authorization

The daemon holds the organization key, which in principle could encrypt writes to any cipher in the org vault. The spec scopes that write authority to the specific cipher being rotated by using the in-flight TaskDispatch itself as the capability — no separate token or grant entity is needed.

🔑
How it works: when the daemon submits a cipher write (SubmitCipherUpdate), the server looks up the TaskDispatch for that rotation task and checks three things: the dispatch belongs to this daemon, it is still in-flight, and it is within its write window (15 minutes from dispatch). All three must hold; otherwise the write is rejected and audited.
Cipher write authorization flow
sequenceDiagram participant S as Bitwarden Server participant D as Rotation Daemon Note over S: PerformDispatch creates TaskDispatch
(dispatch.daemon = chosen, dispatched_at = now) S-->>D: push task Note over D: Execute rotation (resolve creds → generate password
→ update target → encrypt with org_key) D->>S: SubmitCipherUpdate(writer=self, task, ciphertext) Note over S: AcceptCipherUpdate checks:
① dispatch.daemon = writer
② dispatch.status in {dispatched, in_progress}
③ dispatched_at + 15 min > now alt All checks pass Note over S: persist ciphertext (zero-knowledge) S-->>D: 200 OK else Any check fails (wrong daemon, not in-flight, window elapsed) Note over S: RejectCipherUpdate
RotationAudited(outcome: write_rejected) S-->>D: 403 Forbidden Note over D: RotationAttemptFailed → retry
(fresh dispatch on next attempt) end

Why the dispatch is sufficient

The dispatch is created by the server and records which daemon it was routed to (dispatch.daemon). A write is only accepted from that specific daemon, while the dispatch is still live, within the time window. Combined, these three checks scope the write to exactly the cipher and window the server authorised — without needing a separate token entity.

The write is a full-object PUT (today's API has no partial-content update): the daemon GETs the cipher, swaps in the newly-encrypted password, and re-PUTs the whole object. The in-flight dispatch authorises replacing the entire cipher record, not just the password field. A dedicated partial-update endpoint would tighten this further — it's noted as an open question.

API-scoped reads

Defence in depth on the read side: the daemon's credential carries no general cipher-read scope. The server will not enumerate ciphers for it or serve ciphertext for any cipher except the one currently being rotated (an in-flight dispatch). This limits what a compromised org key can actually expose without also breaching the server-side API authorization.

♾
Guarantee: DispatchBoundWrite (on CipherWriteIntake) — a cipher write is accepted only against a TaskDispatch that belongs to this daemon, is in-flight, and is within its window. The target is the dispatch's task cipher; the daemon cannot redirect the write elsewhere. The server stores only ciphertext (zero-knowledge).
♾
Guarantee: ApiScopedReads (on CipherWriteIntake) — the daemon's credential has no general cipher-read scope. Only the cipher actively being rotated (in-flight dispatch) is readable, so the organization key cannot be turned into broad vault disclosure without also breaching server-side API authorization.

9Session Termination

After a successful rotation, if task.terminate_sessions = true and the target system has supports_session_termination = true, a SessionTermination is created. Its purpose is to kick existing authenticated sessions for the rotated account — forcing anyone holding the old password to re-authenticate.

Session termination — relationship to rotation
flowchart LR R["RotationTask\n(succeeded ✓)"] R -->|"terminate_sessions = true\n+ target supports it"| ST["SessionTermination\n(queued → terminating)"] R -->|"terminate_sessions = true\n+ target does NOT support it"| W["⚠ SessionTerminationUnsupported\n(warning, rotation still succeeds)"] R -->|"terminate_sessions = false"| Done["Done"] ST -->|"success"| Terminated["terminated ✓"] ST -->|"retries exhausted"| Abandoned["abandoned\n(rotation already succeeded)"] style R fill:#e8f5ed,stroke:#1a7d3b style Abandoned fill:#fff0e6,stroke:#a04000 style Terminated fill:#e8f5ed,stroke:#1a7d3b

Session termination has its own retry counter — up to max_retry_attempts (5) attempts with exponential backoff — completely independent of the rotation task's counter. A termination failure that exhausts retries results in abandoned, which is surfaced to the server but does not fail the rotation. The rotation task already succeeded when the cipher was written.

10Recovery from Dropped Connections

When the connection drops, the server cannot confirm which tasks completed. The recovery mechanism ensures nothing is permanently lost: every in-flight dispatch is marked lost, made immediately re-due, and re-dispatched once the connection is restored.

What "immediately due" means

Setting next_rotation_at = now makes the config eligible for RotationDue and RedispatchOnReconnect. The reconnect rule explicitly re-dispatches all configs where next_rotation_at ≤ now. Because the grant was also expired, a stale write from the pre-drop attempt cannot succeed — the daemon will get a fresh task and a fresh grant.

✓
This design achieves at-least-once rotation delivery: a task that was in-flight during a drop will be retried after reconnect. The AtMostOneInFlightDispatchPerConfig invariant plus the fresh grant ensure no double-write or duplicate execution can succeed.

11Fleet Spreading

Multiple rotation configs can share a target system. To prevent overwhelming a single system with concurrent rotations, the server enforces a per-target concurrency cap: max_in_flight_per_target = 10.

Fleet spreading — queue and drain
flowchart TB subgraph Target["Target System (e.g. MSSQL server)"] Cap["Concurrency cap: 10"] end D1["Config A (due)"] -->|"slot available"| Dispatch1["Dispatch ✓"] D2["Config B (due)"] -->|"slot available"| Dispatch2["Dispatch ✓"] D3["Config C (due)"] -->|"cap reached"| Queue["Queued\n(stays due)"] Dispatch1 -->|"completes\n→ TargetSlotFreed"| Drain["DrainTargetQueue"] Dispatch2 -->|"completes\n→ TargetSlotFreed"| Drain Drain -->|"one slot at a time"| Queue style Cap fill:#fff0e6,stroke:#a04000 style Queue fill:#f3f0fb,stroke:#5e35b1

PerformDispatch checks registration.has_capacity (in_flight_dispatches.count < max_in_flight_per_target). If the cap is hit, the dispatch is silently skipped — the config remains due and will be picked up by DrainTargetQueue when a slot frees.

The cap is enforced as an invariant: TargetConcurrencyCapped guarantees in_flight_dispatches.count ≤ max_in_flight_per_target for every registered target.

12Manual Rotation Fallback

Not every target system has an automated integration the daemon can reach. A rotation config with mode = manual tracks the obligation and records out-of-band compliance.

Manual rotation lifecycle
flowchart LR Due["next_rotation_at ≤ now\n(scheduled)"] Obligation["awaiting_manual_rotation = true\n(surfaced in RotationConfigView)"] Admin["👤 Admin rotates out-of-band"] Record["RecordManualRotation\n(admin confirms)"] Advance["last_rotation_at = now\nnext_rotation_at = next schedule\nRotationAudited(manual_recorded)"] Due --> Obligation Obligation --> Admin Admin --> Record Record --> Advance Advance -->|"next window"| Due style Obligation fill:#fff8e6,stroke:#a05900

The key rules:

  • A manual config can only target a system where supports_automatic_rotation = false.
  • Manual configs are never dispatched to the daemon (invariant: ManualConfigNeverDispatched).
  • RecordManualRotation advances the schedule exactly as a successful automatic rotation would — the audit trail gets an honest record without pretending the system can self-rotate.

13Audit Trail

14Invariants

The spec declares seven invariants — structural properties that must hold at all times. Violations indicate a bug.

AtMostOneActiveSession (daemon)

At most one DaemonSession may be active at any point. Prevents split-brain where two sessions both hold an active org key.

OneRegistrationPerTargetSystem (server)

A TargetSystem has at most one TargetSystemRegistration. Prevents duplicate concurrency-cap tracking.

OneConfigPerCipher (server)

A Cipher is under at most one RotationConfig. This is what makes the access-event trigger work: a cipher uniquely resolves the config to rotate, so the signal carries only the cipher ID.

AtMostOneInFlightDispatchPerConfig (server)

A RotationConfig has at most one in-flight dispatch at a time. Prevents duplicate concurrent executions of the same credential rotation.

TargetConcurrencyCapped (server)

The number of in-flight dispatches against any one target system never exceeds max_in_flight_per_target (10). Enforces the fleet-spreading cap. (See §11.)

AutomaticConfigTargetsCapableSystem (server)

A RotationConfig with mode = automatic can only target a TargetSystem where supports_automatic_rotation = true. Prevents dispatching to systems the daemon can't actually reach.

ManualConfigNeverDispatched (server)

A RotationConfig with mode = manual has zero dispatches. Manual rotations are recorded out-of-band via RecordManualRotation; the daemon never touches them. (See §12.)

15Open Questions

Fourteen design questions remain unresolved. They are grouped below by topic.

Security & authorization

Read blast radius

The dispatch-bound write and API-scoped read controls contain the blast radius at the authorization layer, but the org key itself remains the theoretical crypto ceiling — a key compromise combined with an API authorization bypass would expose the org vault. Closing it at the crypto layer (so a stolen key reveals nothing beyond the managed cipher) requires per-cipher item keys or a write-only asymmetric scheme; both depend on Bitwarden per-item cipher key support. Deferred.

Credential re-issuance

Once a daemon's credential is revoked the session is terminal. How is a replacement credential provisioned and delivered to the daemon? There's currently no mechanism for this in the spec.

Scheduling & dispatch

Non-cron cadences

Schedule carries a cron expression. Do interval-style presets (e.g. "every 90 days") need a separate representation, or can all UX presets be expressed as cron?

Failure handling (§6.8)

MarkDispatchFailed currently reschedules to now + failure_retry_delay (1 hour) and emits RotationFailed as a seam. §6.8 should define the real policy — retry count, backoff strategy, alerting, and auto-disable after a threshold. Until then, next_rotation_at on failure is a placeholder.

Reconcile task creation

Both the daemon's OnTaskDispatched and the server's PerformDispatch model RotationTask creation. The server should be authoritative. The daemon's entry point needs adjusting to reflect this.

On-demand audit attribution

On-demand and access-triggered dispatches record a source on the TaskDispatch but not the triggering admin. Only manual_recorded carries an actor. Should the audit attribute the on-demand actor end-to-end?

Fleet & routing

Fleet spreading dimension

The concurrency cap is per target system. Should there also be a per-connector or per-daemon cap to protect the connector itself? How does that interact with multi-daemon routing?

Multi-daemon routing

When more than one daemon is connected, how does the server choose which daemon receives a dispatch? Is recovery scoped per-daemon (only re-dispatch to the daemon that was handling it) or global?

Configuration lifecycle

Mode switching

Can an admin move a RotationConfig between automatic and manual after creation? If so, what happens to its schedule and any in-flight dispatch? The ManualConfigNeverDispatched invariant assumes mode is fixed at creation.

Cancel vs. stop-new on state changes

Disabling a target system, pausing a config, or applying new settings currently only stop new dispatches — in-flight dispatches are unaffected. Should any of these operations cancel in-flight work?

Manual obligation escalation

Beyond surfacing awaiting_manual_rotation, should a manual config whose obligation stays unmet past a threshold escalate — send a notification, raise severity, or trigger an alert?

Integrations & future scope

Access-event emitter binding

Which upstream systems wire into AccessGrantEnded? The signal shape is resolved (just the cipher ID), but the concrete set of emitters and how they register against AccessEventIntake is open. PAM leases and AAP grants are the expected first consumers.

Custom script result format

When a CustomScript target runs, how does the daemon interpret the result? Exit code is simplest and most portable, but stdout parsing or structured output may be needed for richer error reporting.

Secrets Manager support (Phase 1 non-goal)

A future configuration would point at an SM secret rather than a vault cipher. The cipher field on RotationConfig and daemon/RotationTask.cipher are the intended seam. The scheduling, dispatch, recovery, and audit machinery is designed to carry an SM rotation unchanged — but this needs confirmation before generalising.
